# 高阶方案设计工作流

引导按结构化流程完成**用于评审的高阶方案**：从需求获取、需求澄清与分析、高阶方案设计到最终文档产出，与用户多轮协作并保证可追溯性。

**本工作流专注于方案评审，不涉及代码实现。** 产出物面向架构/技术评审，描述「做什么」而非「怎么做」。

正式文档模板、内容规范、确认语句、质量清单与特殊情况见 [reference.md](reference.md)。

## 适用范围

- **适用场景**：
  - 新功能/改造需求的技术方案评审
  - 跨模块、跨系统变更的方案预审
  - 需要归档为 Markdown 文档供团队 Review 的设计
  - 需求明确后、进入详细设计与编码前的方案对齐
- **不适用**：
  - 用户已明确要求「直接实现/写代码」→ 切换到 `/rdd` 或 `/do` 或项目编码流程
  - 需要详细实现设计（类、方法、SQL）→ 使用项目详细设计流程或编码流程

## 核心原则

- **确认前不改代码**：在用户明确确认方案并同意产出文档之前，不进行任何代码或配置修改
- **澄清优先**：需求未充分理解前，禁止进入方案设计
- **评审导向**：高阶方案聚焦业务目标、架构边界、接口契约、数据变更、集成关系；**不写实现细节**
- **用户主导**：每个阶段结束必须等待用户确认，不擅自推进
- **可追溯性**：方案结论须能追溯到已确认的需求；假设与推断须显式标注
- **基于现状**：结合项目上下文（技术栈、架构、现有模块、表结构、接口）进行分析
- **语言一致性**：与用户交流使用用户的语言（默认中文）
- **文档产出可控**：最终文档仅在用户确认方案后生成；保存路径与文件名由用户指定或协商

## 工作流程概览

```
阶段 1：需求获取
    ↓ [等待用户输入；用户确认：需求材料已提供完毕]
阶段 2：需求澄清与分析（可多轮）
    ↓ [用户确认：需求理解无误，可以开始方案设计]
阶段 3：高阶方案设计（可多轮）
    ↓ [用户确认：方案无误，可以产出文档]
阶段 4：产出高阶方案文档
    ↓ [用户确认：文档完成 / 或转入详细设计或实现]
```

**严格规则**：每个阶段的「退出条件」达成前，禁止进入下一阶段。

---

## 阶段 1：需求获取

**目标**：收集用户提供的全部原始材料，建立分析起点；**此阶段不做深度分析与方案推断**。

### 执行步骤

1. **等待并接收用户输入**（口头描述、PRD、工单、入口模块、设计稿、外链等）
2. **结合项目上下文做初步定位**（只读）：识别可能模块、服务、分层；标注新增 / 改造 / 废弃
3. **归档材料清单**，不做方案设计

### 退出条件

用户明确表示：「需求材料已提供完毕」/「可以开始澄清」/「继续」

### 输出模板

```
## 已收集材料

| # | 材料 | 来源 | 摘要 |
|---|------|------|------|
| 1 | [...] | [对话/文件/工单] | [...] |

## 初步涉及范围（待澄清）

- 可能模块：[...]
- 可能系统边界：[...]

## 待补充材料（如有）

- [缺失项及原因]
```

> **停止输出，等待用户确认后进入阶段 2。**

---

## 阶段 2：需求澄清与分析（可多轮）

**目标**：对齐需求理解，消除歧义，形成可支撑方案设计的稳定需求基线。

### 前置条件

阶段 1 已完成，用户确认需求材料已提供完毕。

### 执行步骤

1. **结构化需求复述**：业务目标、In/Out of Scope、用户与场景、约束、依赖与前置
2. **现状关联分析**（只读）：相关模块/API/表、Gap、可复用 vs 新建；区分已知事实 / 推断 / 假设
3. **待确认问题清单**：边界、与现有功能关系、非功能、验收与优先级
4. **假设登记**：暂时无法确认但需推进的点，显式列出

### 交互规则

- 可多轮往返，直到待确认项为空或用户接受剩余假设
- 发现需求矛盾或明显不可行时，立即指出
- **未获用户确认前，禁止进入阶段 3**

### 退出条件

用户明确回复：「需求理解正确，可以开始方案设计」或「确认需求，进入方案设计」

### 输出模板

```
## 需求理解摘要

### 业务目标
[一段话]

### 功能范围
- **In Scope**：[...]
- **Out of Scope**：[...]

### 用户与场景
- [...]

### 约束与依赖
- [...]

### 现状关联（Gap 摘要）
| 能力项 | 现状 | 目标 | 改动类型 |
|--------|------|------|----------|
| [...] | [...] | [...] | 新增/修改/复用 |

### 验收标准（建议）
- [...]

### 待确认问题（第 N 轮）
1. [问题] — 当前理解/假设：[...]

### 已确认假设
- [假设 1]
```

> **停止输出，等待用户确认后进入阶段 3。**

---

## 阶段 3：高阶方案设计（可多轮）

**目标**：设计面向评审的高阶方案骨架；**不涉及实现细节**。

### 前置条件

阶段 2 已完成，用户确认需求理解无误。

### 执行步骤

1. **原则**：描述「做什么」，不写类名、方法签名、SQL DDL、具体代码；标注可复用组件；只设计核心必要能力
2. **按需只读探索**：模块、接口、表结构、集成点；有 DB MCP 时先查表现状
3. **组织草案**（见下方模板）；主动覆盖完整性、风险、接口/数据对调用方影响、更简/分阶段可能
4. **多方案（可选）**：最多 3 种，高阶对比后由用户选定

### 交互规则

- 可多轮调整；与需求不符时回到阶段 2
- 用户试图跳过时，提示：「需要先确认高阶方案，再产出文档」

### 退出条件

用户明确回复：「方案确认，可以产出文档」或「确认方案，生成文档」

### 方案草案模板

```
## 高阶方案草案

### 1. 概述
- 背景与目标 / 方案摘要 / 范围与边界 / 关键假设与约束

### 2. 术语
| 术语 | 定义 | 备注 |
|------|------|------|

### 3. 逻辑视图
- 涉及系统/模块、职责与协作；[Mermaid 组件图]

### 4. 流程设计
- 核心业务流程；[Mermaid 流程图/时序图——仅关键路径]；关键决策点与异常分支

### 5. 接口设计
#### 5.1 新增 API / 5.2 修改 API / 5.3 废弃 API
（表格：方法、路径、用途或变更、兼容性、调用方）

### 6. 数据视图
#### 6.1 新增表 / 6.2 修改表 / 6.3 删除表
（业务语义字段说明 + Mermaid ER——仅涉及实体）

### 7. 集成视图
- 外部系统/中间件/通道、集成方式、数据流向；[Mermaid 集成拓扑]

### 8. 风险与待决策项
| 项 | 类型 | 说明 | 建议 |
|----|------|------|------|

### 9. 决策记录
- DR-1：[决策] — 原因：[...]
```

> **停止输出，等待用户确认后进入阶段 4。**

---

## 阶段 4：产出高阶方案文档

**目标**：整理为完整、可归档、可评审的 Markdown 文档。

### 前置条件

阶段 3 已完成，用户确认方案无误。

### 执行步骤

1. 按正式模板整理（见 [reference.md](reference.md)），补充目录、版本、关联需求；移除过程性讨论
2. 文档元信息：标题、工单、版本与日期、作者、状态（Draft / Review / Approved）
3. 询问保存路径与文件名；建议 `docs/hld/{feature-name}-hld.md`；**仅在用户同意时写入**
4. 文末附：**待确认项清单**、**后续建议**（详细设计 / `/rdd` 实现）

### 退出条件

用户确认文档满意，或明确要求进入详细设计 / 实现。

---

## 全局规则

1. **不主动修改代码**：全程默认只读；用户要求写代码时，确认是否结束本流程并切换 `/rdd`
2. **随时可提问**：任何阶段遇不确定项，主动询问用户
3. **尊重项目规范**：分析时参考项目架构与惯例，但高阶文档不写实现细节
4. **最小必要设计**：只设计满足需求的核心能力，避免范围蔓延
5. **可追溯**：方案条目可对应到阶段 2 的需求项
6. **跳过阶段处理**：用户要求跳过时，记录「已跳过阶段 X 及潜在风险」
7. **不默认确认**：模糊回复不能视为确认，须等待明确确认语句

## 与其他工作流

| 命令 | 职责边界 |
|------|----------|
| `/hld` | 需求澄清 → **高阶方案** → 评审文档；不改代码 |
| `/spike` | 只读代码分析与可行性/方案对比 |
| `/rdd` / `/do` | 分析 →（方案）→ **实现** → 验证（`/rdd` 复杂改动可询问独立 Review） |
| `/flow` | 文档驱动闭环（维护 `docs/`） |

**推荐路径**：复杂需求先 `/hld` 或 `/spike` 澄清 → 评审通过后用户明确「开始实现」→ `/rdd`、`/do` 或 `/flow`。
