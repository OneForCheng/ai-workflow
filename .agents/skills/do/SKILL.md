# 简化需求驱动工作流

引导按 **分析需求 → 确认需求 → 实现 → 回溯验证** 四步完成任务，确保先理解、再动手、最后可追溯。

## 核心原则

- **确认前不改代码**：用户明确确认需求理解正确之前，禁止修改任何代码或配置文件
- **有疑问先问**：需求不明确时主动提问，不猜测
- **最小变更**：只改实现需求所必需的代码
- **可追溯**：实现完成后逐条对照原始需求

---

## 阶段 0：等待用户输入

### 触发方式

用户可通过以下任意方式提供需求：

- 在对话中直接描述
- 引用文件或粘贴文档片段
- 提供任务标识（如 Jira 卡号，通过 MCP 读取）
- 提供外部链接

### 执行规则

- 收到需求前，不主动开始实现
- 若用户消息仅为寒暄或提问，正常回答，不进入后续阶段
- 若需求信息不足，先追问关键信息，不进入实现

---

## 阶段 1：分析需求

### 执行步骤

1. 读取并理解用户提供的原始需求
2. 结合项目上下文（技术栈、目录结构、相关代码）分析
3. 提炼：
   - **目标**：要解决什么问题
   - **范围**：涉及哪些模块/文件（预估）
   - **约束**：技术限制、兼容性、不可改动项
   - **验收标准**：怎样算做完

### 产出格式

```
## 需求理解

[一段话概括核心目标]

## 影响范围

- 涉及模块：[模块列表]
- 涉及文件（预估）：[文件列表]

## 验收标准

1. [可验证的完成条件 1]
2. [可验证的完成条件 2]

## 待确认项（如有）

1. [不明确或有歧义的点]
```

### 交互规则

- 输出分析后 **立即停止**，等待用户确认
- 提示用户：

  **「请确认以上需求理解是否正确。  
  如无误，请回复：确认需求，可以开始实现。」**

- 存在待确认项时，必须先澄清再进入下一阶段
- 用户可补充、修正或缩小/扩大范围；反复确认直到一致

### 禁止行为

在用户回复 **「确认需求，可以开始实现」** 之前，严格禁止：

- 输出或修改任何代码
- 创建/删除文件
- 执行会改变项目状态的命令（如安装依赖、数据库迁移）

---

## 阶段 2：实现需求

### 前置条件

用户已明确回复：**确认需求，可以开始实现**

### 执行步骤

1. 按阶段 1 确认的需求与验收标准实现
2. 遵循项目既有编码规范与目录约定
3. 实现顺序建议：数据模型/类型 → 核心逻辑 → 集成与配置
4. 每完成一个逻辑单元，简要说明做了什么

### 交互规则

- 实现中遇到未预见的技术问题或需求歧义，**暂停并向用户确认**
- 若发现必须偏离已确认需求，先说明原因并征得同意
- 不擅自扩大范围（不加无关重构、不额外生成文档）

### 质量检查

实现完成后执行项目常规检查（如编译、格式化、Lint、相关测试）。

---

## 阶段 3：回溯需求

### 前置条件

代码实现已完成，质量检查已通过。

### 执行步骤

1. 将阶段 1 的 **验收标准** 逐条对照实现结果
2. 每条标注状态：✅ 已实现 / ⚠️ 部分实现 / ❌ 未实现
3. 对 ⚠️ 或 ❌ 项说明原因及后续建议
4. 如有自动化测试，运行并报告结果

### 产出格式

```
## 需求回溯

| 验收标准 | 状态 | 说明 |
|---------|------|------|
| [标准 1] | ✅ | [简要说明如何满足] |
| [标准 2] | ✅ | ... |

## 验证

- 自动化测试：[通过/失败/未覆盖]
- 手动验证建议（如有）：[步骤列表]

## 结论

[任务是否完成；如有遗留项，列出]
```

### 交互规则

- 存在 ❌ 未实现项：修复后重新回溯，或请用户决定是否接受
- 用户发现问题：回到阶段 2 修复，再重新回溯
- 全部 ✅ 后，在对话中告知任务完成（不主动生成总结文档，除非用户要求）

---

## 全局规则

1. **不主动修改代码**：在用户确认方案之前，绝不进行任何代码修改
2. **随时可提问**：在任何阶段遇到不确定的地方，都应主动向用户提问
3. **尊重项目规范**：始终遵循当前项目既有的编码规范和最佳实践
4. **最小化变更**：只修改实现需求所必需的代码，避免不必要的重构
5. **可追溯性**：方案和实现都应能追溯到原始需求
6. **语言一致性**：与用户交流使用用户的语言
7. **不主动生成说明性文件**：未经用户同意或主动指示，不要在项目中创建验证报告、总结文档等说明性文件，直接在对话中输出结论即可。必要时可以询问用户是否需要生成文件
