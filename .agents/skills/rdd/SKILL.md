# 需求驱动开发工作流

引导按结构化流程完成需求：从需求分析、方案设计、代码实现到验证，与用户协作并保证可追溯性。复杂改动可选用**独立会话**做 Code Review，避免「实现者自审」盲区。

## 核心原则

- 在用户明确确认之前，不进行任何代码修改
- 有不确定的地方，随时向用户提问
- 每个阶段产出清晰、可追溯的文档
- 方案选择权始终在用户手中
- **需求回溯一律必做**（阶段 4）：无论改动简繁，都须对照已确认需求确认符合性
- **独立 Code Review 默认关闭**；复杂改动时主动询问；用户可随时要求开启
- 独立审查必须由**隔离会话**执行（子代理 / 新会话均可），实现方不得代替审查

---

## 阶段 1：需求获取与分析

### 触发方式

用户可以通过以下任意方式提供需求：
- 直接在对话中描述需求
- 提供需求文档文件路径（使用文件引用）
- 提供任务管理系统中的任务标识（如 Jira 卡号，通过 MCP 工具读取）
- 提供外部链接（如 Confluence、Notion 等）

### 执行步骤

1. 读取并理解用户提供的原始需求
2. 结合项目上下文（技术栈、项目结构、现有代码）进行分析
3. 识别需求中的关键点：
   - 功能范围（做什么）
   - 影响范围（改哪些模块/文件）
   - 约束条件（技术限制、兼容性要求等）
   - 依赖关系（是否依赖其他模块或外部服务）
4. 识别需求中不明确或有歧义的地方

### 产出

向用户输出需求分析摘要，格式如下：

```
## 需求理解

[用一段话概括需求的核心目标]

## 影响范围

- 涉及模块：[列出受影响的模块]
- 涉及文件（预估）：[列出可能需要修改/新增的文件]

## 待确认项（如有）

1. [不明确的点 1]
2. [不明确的点 2]
...
```

### 交互规则

- 如果存在待确认项，等待用户回复后再进入下一阶段
- 用户可以补充上下文、修正理解偏差、或调整需求范围
- 反复确认直到双方对需求理解一致

---

## 阶段 2：方案设计

### 前置条件

阶段 1 的需求已明确，无待确认项。

### 执行步骤

1. 基于明确的需求，结合项目现有架构和代码，设计实现方案
2. 评估是否存在多种可行方案：
   - 如果只有一种明显最优方案：直接输出该方案
   - 如果存在多种各有特点的方案：最多列举 3 种相对最优的方案
3. 对每种方案进行分析：
   - 实现思路概述
   - 需要修改/新增的文件清单
   - 优点与局限
   - 复杂度和工作量评估
4. 如果有多种方案，明确推荐其中一种并说明理由

### 产出

向用户输出方案文档，格式如下：

**单一方案时：**

```
## 实现方案

### 思路

[方案描述]

### 修改清单

- 修改：`path/to/file` — [修改内容简述]
- 新增：`path/to/new-file` — [文件用途]

### 关键设计决策

- [决策 1 及理由]
- [决策 2 及理由]
```

**多方案时：**

```
## 方案对比

### 方案 A：[方案名称]

- 思路：[简述]
- 优点：[列出]
- 局限：[列出]
- 复杂度：[低/中/高]

### 方案 B：[方案名称]

- 思路：[简述]
- 优点：[列出]
- 局限：[列出]
- 复杂度：[低/中/高]

### 方案 C（如有）：[方案名称]

...

### 推荐

推荐方案 [X]，理由：[说明]
```

### 交互规则

- 等待用户选择方案后再进入下一阶段
- 用户可以要求调整方案细节、混合多个方案的优点、或提出新的方案方向
- 用户确认方案后，明确告知即将进入代码实现阶段

---

## 阶段 3：代码实现

### 前置条件

用户已确认选择的实现方案。

### 执行步骤

1. 按照确认的方案，逐步实现代码修改
2. 遵循当前项目既有的编码规范：
   - 代码风格与现有代码保持一致
   - 类型系统严格（如项目使用静态类型检查）
   - 代码自解释，减少不必要注释
3. 实现顺序建议：
   - 类型定义和常量 → 工具函数/共享逻辑 → 核心模块 → 集成与配置
4. 每完成一个逻辑单元，简要说明做了什么

### 质量检查

代码实现完成后，执行项目的质量检查流程：

1. **静态检查**：执行项目的类型检查/编译检查，确保无错误
2. **代码格式化**：使用项目的代码格式化工具格式化修改的文件
3. **Lint 检查**：如项目配置了 Linter，确保检查通过

### 交互规则

- 实现过程中遇到不确定的设计决策，暂停并向用户确认
- 如果发现方案需要调整（如遇到未预见的技术限制），及时告知用户并讨论

---

## 阶段 4：验证与需求回溯

### 前置条件

代码实现已完成，质量检查已通过。

### 执行步骤

根据修改内容的性质，选择合适的验证方式：

1. **自动化测试**（适用于工具函数、共享逻辑、可测试的模块）
   - 为新增/修改的代码编写或更新测试
   - 测试文件位置和命名遵循项目的测试规范
   - 使用项目配置的测试框架
   - 确保测试覆盖核心逻辑和边界情况

2. **手动验证清单**（适用于难以自动化测试的场景）
   - 提供具体的手动验证步骤供用户检查

3. **需求回溯（一律必做）**
   - 对照阶段 1 已确认需求与阶段 2 方案要点，逐条确认改动符合需求
   - 无论改动多简单，不得跳过本步

### 验证执行

执行项目配置的测试命令，运行相关测试，确保无回归。

### 产出

向用户输出验证结果：

```
## 验证结果

### 自动化测试

- 测试文件：[列出]
- 测试结果：[通过/失败]

### 手动验证建议（如有）

1. [验证步骤 1]
2. [验证步骤 2]

### 需求回溯

- [需求点 1] → ✅ 已实现并验证
- [需求点 2] → ✅ 已实现并验证
```

### 交互规则

- 如果测试失败，分析原因并修复，重新验证
- 如果用户发现问题，回到阶段 3 进行修复
- 需求回溯完成后，进入阶段 5 的复杂度判定与门禁（默认可不做独立 Review）

---

## 阶段 5：独立 Code Review（可选）

阶段 4 证明改动能工作且已对照需求回溯；阶段 5 由独立视角判断是否遗漏风险。**默认不执行**。

### 复杂改动判定

满足**任一**即视为复杂改动：

- 多模块 / 跨层
- 涉及数据模型或持久化
- 涉及权限 / 安全 / 资金类
- 方案阶段有多方案抉择，或实现相对方案有重要偏差
- **本轮改动文件数 > 5**

### 前置条件

- 阶段 4 验证与需求回溯已完成（或用户明确接受当前验证结果）
- 存在可审查的代码变更（已提交或未提交均可）

### 门禁

验证通过后：

| 情况 | 行为 |
|------|------|
| **非**复杂改动 | 默认结束工作流；可一句提示「需要独立 Code Review 时可再说」。用户主动要求则进入审查 |
| **复杂改动** | **立即停止并询问**（见下）；不得擅自跳过询问，也不得实现方自审冒充 |
| 用户主动要求 | 无论是否复杂，进入审查 |

复杂改动时的询问文案：

```
阶段 4 验证与需求回溯已完成。本轮判定为复杂改动（原因：<列出命中条件>）。

是否开独立子代理做 Code Review？
- 回复「开始 Code Review」：启动独立审查
- 回复「跳过 Code Review」：结束本工作流
```

在用户明确回复前，禁止启动独立审查，也禁止实现方自行代替审查。

### 执行原则

1. **独立性**：启动与实现方隔离的审查会话（优先使用子代理 / 独立 Agent；若当前工具不支持，则新开对话或新线程，并将下方提示词完整交给审查方）
2. **禁止自审**：实现需求的同一会话不得通读 diff 后宣称「已完成 Code Review」
3. **审查基准**：必须把阶段 1 确认后的需求摘要，以及阶段 2 已确认方案要点，写入审查提示词
4. **审查范围**：默认审查相对仓库默认/base 分支的全部相关变更；若用户只要工作区未提交改动，则限定为未提交变更
5. **只出报告**：审查方不直接改代码；由实现方在用户确认后再改

### Reviewer 提示词（必须按此结构填写后发送）

将下列模板填入具体内容后，作为独立审查会话的输入。方括号为占位符，启动前必须替换为实际内容。

```text
你是独立的 Code Reviewer，不是本次改动的作者。请基于「原始需求」审查当前代码变更，给出可执行的评审结论。

# 角色与约束
- 保持怀疑态度：默认变更可能有遗漏、过度设计或偏离需求
- 只基于证据发言：每条 finding 必须指向具体文件/符号/行为；无法确认时标注「需人工确认」
- 不要重写整个功能；不要直接改代码；只输出审查报告
- 忽略纯风格偏好（除非违反项目既有规范且会造成实质问题）
- 优先高信号问题：正确性 > 需求对齐 > 安全/数据风险 > 可维护性 > 性能 > 风格
- 不要因为「看起来能跑」就降低对需求对齐的要求
- 不要刷低价值 nit 淹没高优先级问题
- 不要在没有读到相关代码证据时臆测

# 原始需求（审查基准）
## 需求理解
[粘贴阶段 1 确认后的需求理解]

## 已确认方案要点（如有）
[粘贴阶段 2 用户确认的方案摘要 / 关键设计决策]

## 验收/回溯点（如有）
[粘贴阶段 4 需求回溯条目]

# 仓库与审查范围
- 仓库路径：[绝对路径或仓库标识]
- Diff 范围：[相对 base 的分支变更 | 仅未提交变更]
- Base 分支：[仓库默认 base，或指定分支名]
- 本次意图补充（可选）：[用户额外交代的审查关注点]

# 审查任务
1. 读取上述范围内的代码变更（及理解所需的最小上下文）
2. 对照「原始需求」与「已确认方案」评估变更
3. 按下方检查维度输出 findings（无问题的维度可显式写「未发现明显问题」）
4. 区分：缺陷 / 风险 / 需求缺口 / 建议（非阻塞）

# 检查维度（业界实践综合）
## A. 需求对齐（Requirement Fit）
- 是否完整覆盖已确认需求？有无范围外改动（scope creep）？
- 是否偏离已确认方案的关键决策？若偏离，是否有充分理由？
- 有无需求中写明但实现缺失、或实现了但需求未要求的行为？

## B. 正确性与回归（Correctness）
- 正常路径、错误路径、边界条件是否处理合理？
- 是否可能破坏既有行为/API/数据兼容性？
- 并发、幂等、重试、超时、空值等是否被忽略？
- 测试是否支撑核心行为？有无高风险逻辑缺少测试？

## C. 设计与可维护性（Design）
- 抽象是否过度或不足？是否与项目现有分层/模式一致？
- 模块边界、命名、职责是否清晰？是否引入不必要耦合？
- 是否有更简单且同样满足需求的做法被忽略？

## D. 安全与数据（Security & Data）— 按变更相关性审查
- 输入校验、授权、敏感信息泄露、注入、不安全反序列化等
- 密钥/Token/PII 是否进入日志或错误信息
- 仅在变更触及相关面时深入；无关则简短声明跳过

## E. 运维与可观测性（Operability）— 按需
- 失败是否可诊断？关键路径是否有足够日志（且无敏感数据）？
- 配置/迁移/兼容性是否有回滚或双写风险？

# 产出格式（必须遵守）
先给 2～4 句总评（是否建议合并/是否对齐需求），再输出表格与清单。

## 总评
- 需求对齐：[充分 / 部分 / 不足]
- 合并建议：[可以合并 / 修复后再合并 / 需讨论]
- 一句话结论：[...]

## Findings

| ID | Severity | Category | Location | Finding | 建议 |
|----|----------|----------|----------|---------|------|
| F1 | blocker/major/minor/nit | 需求对齐/正确性/设计/安全/测试/其他 | path:symbol 或 path | 问题陈述（含证据） | 可执行的修复方向 |

Severity：blocker（错误/安全/明显未满足需求）· major（高概率缺陷、重要遗漏、显著偏离方案）· minor（建议修、非必须阻塞）· nit（非阻塞改进）

## 可能未考虑到的点
- [即使当前 diff 未体现、但按需求很可能会踩坑的场景；0～5 条，没有则写「无」]

## 无需修改的正面观察（可选，最多 3 条）
- [真正做得好的、与需求强相关的点]
```

### 结果处理

独立审查返回后，由实现方：

1. 按 severity 汇总 findings，用紧凑表格呈现给用户
2. **默认不自动改代码**，请用户决策：

```
## Code Review 汇总

[总评摘要]

| Severity | Location | Finding |
|----------|----------|---------|
| ... | ... | ... |

请选择下一步：
- 回复「按 Review 修复」或指定 finding ID：回到阶段 3 修复，再按需重跑阶段 4/5
- 回复「忽略 xxx」：记录为已接受风险
- 回复「完成」：结束工作流
```

3. 仅在用户明确指示修复后回到阶段 3；修复后重新做阶段 4，并再次询问是否重跑阶段 5（可跳过）
4. 审查失败时：说明原因，征得同意后重试一次，或由用户决定跳过

### 产出

```
## Code Review 结果

- 是否执行：[已执行 / 用户跳过 / 未触发（非复杂且未要求）]
- 需求对齐：[充分 / 部分 / 不足 / 未审查]
- Findings：[blocker N / major N / minor N / nit N]
- 用户决策：[已修复 / 部分接受 / 全部接受 / 跳过审查 / 未审查]
```

---

## 全局规则

1. **不主动修改代码**：在用户确认方案之前，绝不进行任何代码修改
2. **随时可提问**：在任何阶段遇到不确定的地方，都应主动向用户提问
3. **尊重项目规范**：始终遵循当前项目既有的编码规范和最佳实践
4. **最小化变更**：只修改实现需求所必需的代码，避免不必要的重构
5. **可追溯性**：方案、实现与 Review 结论都应能追溯到原始需求
6. **语言一致性**：与用户交流使用用户的语言
7. **不主动生成说明性文件**：未经用户同意，不要在项目中创建验证报告、总结文档、Review 报告等文件；在对话中输出结论即可
8. **需求回溯不可跳过**：阶段 4 必须输出对照需求的回溯
9. **审查独立性**：若执行阶段 5，必须使用独立审查会话；实现方只负责发起、汇总与跟进用户决策
10. **Review 默认可选**：跳过或未触发不等于验证失败

---

## 工具适配说明

本规则不绑定特定 Agent 产品。凡支持「多会话 / 子代理 / 独立线程」的工具，按阶段 5 执行原则启动隔离审查即可；若不支持，将同一套 Reviewer 提示词粘贴到新对话中完成审查，再把结论交回实现会话处理。

## 与其他工作流

| 命令 | 职责边界 |
|------|----------|
| `/do` | 更轻：确认需求后直接实现并回溯，无独立方案阶段 |
| `/rdd` | 完整轻量交付：分析 → 方案 → 实现 → 回溯；复杂时可选独立 Review；也可在方案确认后停止（只分析不写码） |
| `/flow` | 文档驱动闭环（维护 `docs/`） |
| `/hld` | 高阶方案评审文档，不改代码 |
| `/init` | 生成项目 AI 上下文规则 |
