# 需求驱动开发工作流

引导按结构化流程完成需求：从需求分析、方案设计、代码实现到验证，与用户协作并保证可追溯性。

## 核心原则

- 在用户明确确认之前，不进行任何代码修改
- 有不确定的地方，随时向用户提问
- 每个阶段产出清晰、可追溯的文档
- 方案选择权始终在用户手中

---

## 阶段 1：需求获取与分析

### 触发方式

用户可以通过以下任意方式提供需求：
- 直接在对话中描述需求
- 提供需求文档文件路径（使用文件引用）
- 提供任务管理系统中的任务标识（如 Jira 卡号，通过 MCP 工具读取）
- 提供外部链接（如 Confluence、Notion 等）

### 执行步骤

1. 读取并理解用户提供的原始需求
2. 结合项目上下文（技术栈、项目结构、现有代码）进行分析
3. 识别需求中的关键点：
   - 功能范围（做什么）
   - 影响范围（改哪些模块/文件）
   - 约束条件（技术限制、兼容性要求等）
   - 依赖关系（是否依赖其他模块或外部服务）
4. 识别需求中不明确或有歧义的地方

### 产出

向用户输出需求分析摘要，格式如下：

```
## 需求理解

[用一段话概括需求的核心目标]

## 影响范围

- 涉及模块：[列出受影响的模块]
- 涉及文件（预估）：[列出可能需要修改/新增的文件]

## 待确认项（如有）

1. [不明确的点 1]
2. [不明确的点 2]
...
```

### 交互规则

- 如果存在待确认项，等待用户回复后再进入下一阶段
- 用户可以补充上下文、修正理解偏差、或调整需求范围
- 反复确认直到双方对需求理解一致

---

## 阶段 2：方案设计

### 前置条件

阶段 1 的需求已明确，无待确认项。

### 执行步骤

1. 基于明确的需求，结合项目现有架构和代码，设计实现方案
2. 评估是否存在多种可行方案：
   - 如果只有一种明显最优方案：直接输出该方案
   - 如果存在多种各有特点的方案：最多列举 3 种相对最优的方案
3. 对每种方案进行分析：
   - 实现思路概述
   - 需要修改/新增的文件清单
   - 优点与局限
   - 复杂度和工作量评估
4. 如果有多种方案，明确推荐其中一种并说明理由

### 产出

向用户输出方案文档，格式如下：

**单一方案时：**

```
## 实现方案

### 思路

[方案描述]

### 修改清单

- 修改：`path/to/file` — [修改内容简述]
- 新增：`path/to/new-file` — [文件用途]

### 关键设计决策

- [决策 1 及理由]
- [决策 2 及理由]
```

**多方案时：**

```
## 方案对比

### 方案 A：[方案名称]

- 思路：[简述]
- 优点：[列出]
- 局限：[列出]
- 复杂度：[低/中/高]

### 方案 B：[方案名称]

- 思路：[简述]
- 优点：[列出]
- 局限：[列出]
- 复杂度：[低/中/高]

### 方案 C（如有）：[方案名称]

...

### 推荐

推荐方案 [X]，理由：[说明]
```

### 交互规则

- 等待用户选择方案后再进入下一阶段
- 用户可以要求调整方案细节、混合多个方案的优点、或提出新的方案方向
- 用户确认方案后，明确告知即将进入代码实现阶段

---

## 阶段 3：代码实现

### 前置条件

用户已确认选择的实现方案。

### 执行步骤

1. 按照确认的方案，逐步实现代码修改
2. 遵循当前项目既有的编码规范：
   - 代码风格与现有代码保持一致
   - 类型系统严格（如项目使用静态类型检查）
   - 代码自解释，减少不必要注释
3. 实现顺序建议：
   - 类型定义和常量 → 工具函数/共享逻辑 → 核心模块 → 集成与配置
4. 每完成一个逻辑单元，简要说明做了什么

### 质量检查

代码实现完成后，执行项目的质量检查流程：

1. **静态检查**：执行项目的类型检查/编译检查，确保无错误
2. **代码格式化**：使用项目的代码格式化工具格式化修改的文件
3. **Lint 检查**：如项目配置了 Linter，确保检查通过

### 交互规则

- 实现过程中遇到不确定的设计决策，暂停并向用户确认
- 如果发现方案需要调整（如遇到未预见的技术限制），及时告知用户并讨论

---

## 阶段 4：验证

### 前置条件

代码实现已完成，质量检查已通过。

### 执行步骤

根据修改内容的性质，选择合适的验证方式：

1. **自动化测试**（适用于工具函数、共享逻辑、可测试的模块）
   - 为新增/修改的代码编写或更新测试
   - 测试文件位置和命名遵循项目的测试规范
   - 使用项目配置的测试框架
   - 确保测试覆盖核心逻辑和边界情况

2. **手动验证清单**（适用于难以自动化测试的场景）
   - 提供具体的手动验证步骤供用户检查

### 验证执行

执行项目配置的测试命令，运行相关测试，确保无回归。

### 产出

向用户输出验证结果：

```
## 验证结果

### 自动化测试

- 测试文件：[列出]
- 测试结果：[通过/失败]

### 手动验证建议（如有）

1. [验证步骤 1]
2. [验证步骤 2]

### 需求回溯

- [需求点 1] → ✅ 已实现并验证
- [需求点 2] → ✅ 已实现并验证
```

### 交互规则

- 如果测试失败，分析原因并修复，重新验证
- 如果用户发现问题，回到阶段 3 进行修复
- 验证通过后，向用户确认任务完成

---

## 全局规则

1. **不主动修改代码**：在用户确认方案之前，绝不进行任何代码修改
2. **随时可提问**：在任何阶段遇到不确定的地方，都应主动向用户提问
3. **尊重项目规范**：始终遵循当前项目既有的编码规范和最佳实践
4. **最小化变更**：只修改实现需求所必需的代码，避免不必要的重构
5. **可追溯性**：方案和实现都应能追溯到原始需求
6. **语言一致性**：与用户交流使用用户的语言
7. **不主动生成说明性文件**：未经用户同意或主动指示，不要在项目中创建验证报告、总结文档等说明性文件，直接在对话中输出结论即可。必要时可以询问用户是否需要生成文件
